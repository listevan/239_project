Pilot study

Tool atrophy or internalization?

When a model is RL-trained to use a tool, does it lose the skill the tool replaces, or learn it?

Steven Li · October 2026

The question

Train a math model to call a code interpreter. Then take the interpreter away.

Atrophy

It offloaded arithmetic to the tool and can no longer do it alone.

Internalization

It absorbed what the tool taught it and is better without it than before.

Why it matters

Tool-using agents are now trained with RL everywhere

  • Code interpreters, search, shells: the tool sits inside the training loop, and the model is rewarded only for the outcome.
  • If a skill is offloaded to the tool, the model stops practicing it. Use it or lose it.
  • Tools fail, get rate-limited, or are missing at deployment. What is left of the model then?
  • Nobody has measured this with a proper control.

What the hook leaves open

One figure, four gaps

  • One size. 7B only. No idea how the crossover moves with scale.
  • No text-RL curve. Is the high-k loss from the tool, or from RL itself?
  • Mechanism unstated. How was the tool removed from a model that writes code in nearly every response? Only 1 of 7 prior papers says.
  • Not interpreted. The authors read it as a capability-boundary story. Nobody has named the crossover as a cost.
Prior evidence

Hints in other papers' side tables

  • Trice, tool-only SFT. BeyondAIME drops from 54.3 to 34.1 at 4B. Mixed tool and text data: 49.0. Atrophy is real and data-mix driven.
  • Trice, after RL. Tool-off beats base on 4 of 5 benchmarks, by more at 30B. Internalization at scale.
  • Tool-Overuse Illusion. ReTool-32B makes 3.1 calls per easy GSM8K problem; 7B makes 1.2. Bigger models offload more.
  • Invisible Leash. Text-RL keeps 93% of base coverage at 1.5B and 99% at 14B.

None of them puts tool-RL, text-RL and base on the same pass@k axis.

Hypotheses

Three stories, three signatures

Atrophy

Tool-RL below text-RL at high k. More arithmetic errors than base.

Internalization

Tool-RL above base at every k. Fewer arithmetic errors.

Null

Tool-RL and text-RL match within CI everywhere. The tool changed nothing.

The control

Why text-only RL is the key arm

  • Same base, same kind of zero-RL on math, no tool in the loop.
  • Whatever RL does on its own, sharper answers or lost coverage, shows up here too.
  • Tool-RL minus text-RL is the tool's effect. Tool-RL minus base mixes the two.
  • Oat-Zero is exactly this for Qwen2.5-Math-1.5B: zero-RL from the same base, 288 steps, no tool.

Two ways to switch the tool off

Lost ability, or just the wrong prompt?

A. Prompt off

Shared no-code prompt, identical for every model. Any code it writes anyway is intercepted, never run.

B. Env denied

The model's own tool prompt. It writes code, is told it was not executed, and must keep reasoning.

"No interpreter is available; the code was not executed. Continue reasoning without running code and give the final answer."

An effect under A but not B is prompt mismatch, not atrophy. Both are reported.

Metric 1

pass@k: sharpness at low k, coverage at high k

  • n samples per problem, 16 or 64. Unbiased estimator for every k up to n.
  • Paired bootstrap over problems for the difference between two arms. A CI that excludes zero is a finding.
  • pass@1 asks "is it sharper". pass@64 asks "can it still reach the answer at all".
pass@k = E over problems [ 1 − C(n−c, k) / C(n, k) ]
Metric 2

Does the model still do arithmetic right?

  • Scan each chain of thought for chains like 74 + 5·73 = 2401 + 1715 = 4116, LaTeX included.
  • Check every step exactly with rational arithmetic. No floats, no eval.
  • Report wrong over checked, plus coverage. Split by whether the final answer was right.
  • Also tracked: truncation rate, missing-answer rate, and code emission with the tool off.

Pipeline

Generate on Colab, analyze on the laptop

  • Sampler. vLLM with the tool loop. One model load serves all datasets. Writes JSONL plus metadata.
  • Resumable. Chunks checkpointed to Drive. Finished arms are skipped on re-run.
  • Analysis. math-verify grading, pass@k, bootstrap CIs, dated figures and tables, one folder per run.
  • Tests. The tool loop, executor and grader are unit-tested without a GPU.
Reading the result

Three outcomes, each with a decision

  • Atrophy. Tool-RL falls below text-RL at high k, or makes more arithmetic errors than base while text-RL does not. Go.
  • Internalization. Tool-RL beats base at every k with fewer arithmetic errors. Go.
  • Kill. Tool-RL and text-RL match within bootstrap CIs everywhere. Stop.

Either positive answer is a result. The kill criterion is written down before the first run.

After the pilot

If the signal is there

  • Dose-response. pass@k over released 1.5B RL step checkpoints (VerlTool ToRL, 140 to 650 steps), with a per-step text-RL series as the control.
  • Scale. Replicate at 7B with CIR, the Fig. 6 model itself. Prediction: the high-k deficit shrinks but does not vanish.
  • Fix. Mix tool-free rollouts into tool RL and test whether the high-k loss disappears. Needs training.
Beyond math

The same question in two other domains

Search

Search-R1 vs its R1 twin: same author, data, algorithm, 3B and 7B. Closed-book QA with retrieval off. The cleanest control anywhere.

Coding agents

DeepSWE and SWE-Master vs base. CRUXEval-O, predicting code output without running it, is the arithmetic analog. 32B inference, no step checkpoints.

Math first: the hook is published, the controls exist, and it is the cheapest.

Issues so far: the harness

Most of the week went into making Colab survive a run

  • Stalls. The arithmetic checker used regex plus eval and hung on long outputs. Rewritten as a linear scan with no eval.
  • Hung executions. Model code that called input() waited out the whole timeout. Stdin is now closed so it fails fast.
  • Disconnects. Colab drops sessions mid-run. Runs checkpoint to Drive in chunks, resume from the last one, and skip finished arms.
  • Drive. Mounts failed silently and the project folder was filed in different places. Now fails loudly and is found anywhere under My Drive.
  • Stale files. Results from an older notebook version mixed into a run. They are flagged and quarantined.
  • Grading. Too slow on Colab. Moved to the laptop with per-row timeouts.
Issues so far: the method

What could still bias the answer

  • Context. Qwen2.5-Math's native context is 4k tokens; CIR evaluated at 16k by extrapolation. We cap at 4k and report the truncation rate.
  • Prompts. Each checkpoint was trained on its own template. ToRL's is verbatim from the paper, but prompt mismatch can masquerade as atrophy. Hence both tool-off protocols.
  • Non-compliance. Under prompt-off, models write code anyway. It is counted, intercepted, and never executed.
  • No sandbox. Tool-on runs model code on the Colab VM with a 10 s timeout. Fine there, not on a shared machine.
  • Only 1.5B, only math. 7B is too expensive for the pilot, and every open tool-RL checkpoint is a math model.
Takeaway

One base, three checkpoints, tool off

  • A published crossover nobody has explained.
  • A control that separates the tool's effect from RL's.
  • Two tool-off protocols and two metrics.
  • A kill criterion written down in advance.
  • A harness that now survives Colab. Results next.
